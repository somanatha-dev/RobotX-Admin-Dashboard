# DTARO gap analysis: the paper vs RobotX

Audited at `5e94a1a`, 2026-10-22.

- **Paper** = `DTARO-final.pdf` (2026-09-28).
- **RobotX** = current source, as established in [`CURRENT_IMPLEMENTATION_MAP.md`](CURRENT_IMPLEMENTATION_MAP.md) (cited as **MAP §n**).

Paper behaviour is described as the paper states it. RobotX behaviour is only what was verified. Proposals are labelled as such and are not decisions.

---

## 1. What the paper specifies (summary of the reference)

| Element | Paper statement (section) |
|---|---|
| Architecture | Centralised Node.js server with a Task Manager, readiness gate, Cost Evaluator, EKB, and Robot Registry; Socket.IO over WebSocket; physical and software agents share one protocol (§III, Fig. 1) |
| Events | `task new`, `status update` (2 Hz), `obstacle report`, `zone alert`, `task complete` (§III-B) |
| Zones | "The map is split into Z equal rectangular zones, each with its own Socket.IO room." An agent "joins the room for its current zone and hears an alert only when the obstacle lies in that zone" (§III-B, §III-C) |
| EKB | Obstacle = (location, timestamp, reporting agent, zone, severity); server writes, identifies the zone, emits to that zone's room; TTL 300 s default (§III-D) |
| Receiver-side relevance | "Each notified agent tests whether the obstacle cell lies on its own planned path" (§IV-D). This is the distinguishing claim versus classical zone interest management (§II-D) |
| Local replanning | Algorithm 2, run by each notified robot: if intersecting, set cost[obs] = ∞, A* from the current position to the destination, replace the path, resume; else no action |
| Allocation | Admission gate (auth, connectivity, battery ≥ b_min, no fault, healthy sensors) then C(r) = 0.45·d + 0.25·(1−b) + 0.20·u + 0.10·τ, arg min; DEFER if none (Algorithm 1) |
| Communication model | N_broadcast = n; N_zone ≈ n/Z; N_filtered ≈ (n/Z)·p_int, with p_int ≈ L/A; worst case ρ·n/Z (Eqs. 2–6) |
| Coordinator bound | R = n·f + λ + n·μ; M/G/1 n_max ≈ (1/s̄ − λ)/(f + μ) (Eqs. 7–8). Zoning does not reduce inbound coordinator load |

## 3. The paper's results, kept separate

**None of the figures below is a RobotX measurement.** The paper's own text says its experiment is "a discrete-grid simulation with Manhattan routing … eight software agents … no physical robots are in the loop" (§VI-C). RobotX's simulator uses an OSM campus sidewalk network, exact coordinates, an H3 index and a different allocator, so the results do not transfer.

|---|---|---|

### Points where RobotX evidence bears on the paper's assumptions

These are inferences. They are relevant to design, and they are not refutations.

1. **n/Z at RobotX scale.** A campus is ~0.1 km² (RNSIT and JSSATE), and the V1 fleet is ~10 simulated robots. With a few zones per campus, n/Z is small, so the message saving from zone scoping is small in absolute terms. The paper itself says scoping matters as n grows.
2. **Current-zone-only false negatives.** On a small campus a route commonly spans several zones, so "hears an alert only when the obstacle lies in that zone" misses robots whose route enters that zone later. The historical communication audit raised this (§12.1), and the paper's own p_int ≈ L/A grows with route length.
3. **Receiver-side placement fits RobotX.** The robot already holds its executing path. This avoids the server-side O(N) scan the registry banner flags against T9.
4. **The paper's local replanning conflicts with RobotX's completion trust model.** A robot that changes its own route makes the driven corridor differ from the signed OFFER, and completion is graded against that corridor (F3). The paper does not model this.

## 4. Failure-case matrix (prompt §10)

| Case | Current behaviour | Existing defence | Gap |
|---|---|---|---|
| Robot disconnects while subscribed to a zone | Socket.IO drops the room membership; registry marked `connected:false`; `robots:all` srem on disconnect | Rooms are server-joined | Alerts sent while it is away are lost (no replay) |
| Robot reconnects after missing an alert | Rejoins `robot:{id}`; **does not rejoin `zone:{id}`** within the TTL [E: P5]; no EKB replay (`getActiveObstacles` has no caller) | Engine commands use dedup/outbox; obstacle alerts do not | Rejoin plus active-obstacle replay on AUTH |
| Robot crosses a zone boundary | Leave/join on change, `ZONE_UPDATED` (dashboard, unconsumed) | Change detection is tested | No delivery of the new zone's active obstacles on entry |
| Robot changes its planned route | Engine routes change only by a new OFFER; registry `plannedPath` never written | OFFER fence/sequence | Route-derived subscriptions (if adopted) must follow OFFER/WITHDRAW/settle |
| Alert arrives late or out of order | Only `timestamp`; no version/sequence | — | Versioned obstacle records; receiver ignores stale versions |
| Duplicate obstacle reports | New record each time [E: P6] | Rate limit per robot | Merge key (cell + window), report count, confirmations |
| Conflicting observations | Not representable | — | Lifecycle with confirm/clear evidence |
| Expired or cleared obstacles | Silent KV expiry at 300 s | — | Expiry event; evidence-based clear; dashboard lifecycle |
| False-positive observation | Accepted as-is; the simulator fabricates them by design | Rate limit | Plausibility; corroboration policy; operator clear |
| Obstacle disappears after a route was blocked | n/a (no blocking today) | — | Decide: keep the detour, or offer a restore replan |
| Robot receives an alert for another campus | Possible in principle: fleet-wide scan, no region check; reporter unchecked [E: P2c] | Geometry makes a cross-campus *intersection* unlikely [I] | Recipient selection must be bounded by region; reject points outside the reporter's region |
| Route changes between the intersection check and execution | n/a | Engine fence/sequence would refuse a stale `REROUTE` | Receiver checks against its current path; server-produced `REROUTE` must carry the fence of the live commitment |
| Replanning failure / no feasible path | Legacy falls back to a straight line (`routing.service.js:116`) | Campus router refuses (`NOT_ROUTABLE`), never a straight line | Hold + escalate (A8 → operator queue) instead of fabricating a path |
| Command refers to a stale plan | Fenced mission commands refused below the high-water mark | `VirtualRobot._onMissionCommand` | — (defence exists for `REROUTE`) |
| Simulated robot online but not ready | Engine readiness predicates and agent refusals handle assignment | F-predicates | Alerts should still reach it if it is executing; non-executing robots need no replan |
